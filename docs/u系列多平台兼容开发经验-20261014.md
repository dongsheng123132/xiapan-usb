# u 系列多平台（Mac + Windows）兼容开发经验沉淀

> 版本：v1.0 · 2026-10-14
> 范围：u-picoclaw（虾盘 U 盘精灵）、u-claw（U-DSH 大龙虾）、u-openclaw（OpenClaw 便携线）
> 目标：任何一条产品线做 Mac + Windows 双平台时，直接照本文件判断"能不能兼容、怎么兼容、怎么验收"，不再重复踩坑。
> 来源：git 提交（xiapan-usb `121b065`/`22c93f2`/`ae2fe21`，customer-udsh `79218a3`）、docs/ 实测记录、发盘 0.5.4 成品结构。所有结论都有对应证据可溯源。

---

## 一、核心结论（30 秒读完）

1. **exFAT 兼容不是"能不能格式化"的问题，是运行时对文件系统能力的三条硬依赖问题**：junction/symlink、Unix 权限位、AppleDouble 元数据。
2. 先回答一个问题：**你的运行时在启动/运行时会不会建 junction 或 symlink、是否依赖 Unix 可执行权限位？**
   - 会 → exFAT 上必然失败（如 U-DSH 的 EISDIR），要么宿主缓存绕开，要么干脆 NTFS-only；
   - 不会 → 核心可以直接跑 exFAT（如虾盘 Go 核心，双盘实测通过）。
3. 双平台的目标不是"同一格式到处跑"，而是**每块盘、每台机、每种文件系统都有明确的能力判定和用户可理解的行为**。

## 二、平台 × 文件系统能力对照（实测结论）

| 能力 | Windows + NTFS | Windows + exFAT | macOS + exFAT | macOS + APFS | 说明 |
| --- | --- | --- | --- | --- | --- |
| 目录链接 junction | ✅ | ❌ 实测 EISDIR | ❌ | ✅（symlink） | exFAT/FAT32 物理不支持，任何语言任何用户都失败 |
| symlink | ✅（需权限） | ❌ | ❌ | ✅ | DSH 上游 `ensureSymlink` 见非 symlink 直接 throw |
| Unix 可执行权限位 | 无（.exe 按扩展名） | 无 | ❌ 首次需补 chmod | ✅ | exFAT 不保存权限，程序复制到宿主后要补 +x |
| Mac 写入兼容 | ❌ Mac 不能写 NTFS | ✅ | ✅ | ✅ | 双平台共用一盘必须 exFAT，否则 Mac 只读 |
| AppleDouble 元数据 | 无 | Windows 端可见 `._*`/`.DS_Store` | macOS 自动写 | 无 | macOS 在 exFAT/FAT 上为每个文件写附属文件 |
| 判断文件系统 | `Get-Volume` | `Get-Volume` | `diskutil` | `diskutil` | ⚠️ `Win32_LogicalDisk.FileSystem` 有缓存过期值，会把 exFAT 报成 NTFS |
| 原子写的文件身份（inode） | ✅ | ❌ inode 恒为 0 | ❌ | ✅ | OpenClaw 原子写做严格身份校验，exFAT 上必然 `path-mismatch`；需走 `verify-content-with-lock` 兼容路径 |

## 三、三条产品线的落地记录

### 1. u-picoclaw（虾盘 U 盘精灵）—— 主动兼容 exFAT，双平台已发货

**架构**：Go 核心 + PicoClaw v0.3.1 便携运行时（frozen，manifest 锁 SHA-256）。核心不建 junction、不依赖权限位 → exFAT 可直跑。

**验收证据**（`docs/双U盘实测-20261003.md`）：
- E 盘 ORICO（exFAT）/ F 盘闪迪（NTFS）同机同构建，8 个程序文件 SHA-256 一致；
- 启动项读取、原生工具窗口、重启续会话、跨盘接续（E→F 复制 data/）、真实虾盘云问答全部通过；
- 0.5.4 成品：根目录 `虾盘.exe` + `启动 Mac.command`，`app/runtime/picoclaw/` 按平台放二进制（arm64 + x64）。

**四个关键修复**（按时间）：
1. **WMI 提速与排除法**（0.3）：设备读取 CIM 15.55s → WMI 2.27s，完整驱动检测 19s → 5.41s；宿主临时目录与 U 盘临时目录同测均约 18s，**排除 exFAT 临时目录是慢的主因**。→ 教训：性能问题先做对照实验再下结论，别甩锅文件系统。
2. **双盘对照验收**（0.4）：见上。
3. **宿主缓存策略**（0.5.4，commit `22c93f2`）：
   - PicoClaw core/launcher 按平台 + 固定 SHA-256 复制到宿主用户缓存（Windows `LocalAppData`，Mac `Library/Caches`）；
   - 第一次复制并校验；后续命中只读本机缓存，不重复读 U 盘大程序；新版本由新 hash 隔离；缓存损坏重新校验；缓存不可用时验证盘上原程序并明确降级；
   - **Key、钱包、会话、记忆、工作文件绝不进缓存，全部留在盘内 `data/`**——不采用"退出时才同步"方案，防异常拔盘丢状态；
   - 缓存上限 256MB，`XIAPAN_RUNTIME_CACHE_DIR` 可覆盖（测试用）；`runtime.cache.status` 只读查询。
4. **Mac 首次从 U 盘运行**（commit `121b065`，Co-Authored-By Claude Opus 5.5）：
   - 启动时主动请求可移除宗卷访问权限；用户拒绝时引导去「系统设置 › 隐私与安全性 › 文件与文件夹」，不静默失败（首次读 U 盘等用户隐私决定，`os.ReadDir` 返回 `fs.ErrPermission` 时给指引）；
   - 资源扫描跳过 `._*` 和 `.DS_Store`（AppleDouble 元数据不是资源）；
   - 文档写明 `dot_clean -n /Volumes/<盘名>` 清理出厂盘的附属文件，避免 Windows 端看到垃圾文件；
   - Mac 启动脚本首次复制到缓存后**补可执行权限**（exFAT 无权限位）；脚本不关 Gatekeeper；
   - ad-hoc 签名每次重建被视为新程序再次询问；Developer ID 签名后授权保留（后续可做公证）。

### 2. u-claw（U-DSH 大龙虾）—— 判定 exFAT 不可行，NTFS-only + 启动前探测

**为什么不行**：DSH 每次启动要在 `$DSH_HOME/profiles/node_modules` 下建 junction，exFAT/FAT32 放不下（实测 `exFAT EISDIR / NTFS OK`，同用户同进程）。vendor 闭包修不掉（数据侧不是内核侧）；"运行时放本机、只数据放 U 盘"也救不了（炸点就在 data 里）；放真实目录代替 symlink 走不通（上游 `ensureSymlink` 见非 symlink 直接 throw）。

**决策**（`docs/ROADMAP.md`「不许推翻的既有决定」）：U 盘必须 NTFS。exFAT 唯一好处是 Mac/Linux 兼容，而本轮只支持 Windows x64 → 兼容成本为零，不做。

**落地动作**（commit `79218a3`）：
- `src/portable-preflight.js` `probeJunctionSupport()`：启动前在数据盘建 `.udsh-junction-probe-<pid>-<ts>` 目录，尝试 `symlink(target, link, 'junction')`，成功 ok / 失败返回 error，finally 清理探针目录。非 win32 平台直接跳过（symlink 由 DSH 自己处理）。**几毫秒真探，代替运行到一半的裸 EISDIR**。
- `src/startup-errors.js` 错误人话化：匹配 `EISDIR|ensureSymlink|junction|symlink` → "数据盘的文件系统不支持 DSH 需要的目录链接（junction）" + 动作"请把 U 盘/移动盘转换或格式化为 NTFS 后重新解压使用（exFAT、FAT32 都不行）。格式化前先备份盘上资料。"
- README FAQ 双语写明"为什么必须 NTFS"，发版前把答案给用户，而不是让用户踩坑后搜。

### 3. u-openclaw（U-Claw / OpenClaw 便携线）—— 0.5.5 已修复 exFAT 崩溃并实测，仍有边界

**进展（2026-10-15，0.5.5）**：U-Claw 便携 AI 工作台（OpenClaw 2026.10.2 + 自带 node win-x64/mac-arm64/mac-x64）已整合进虾盘母盘"随盘 AI 应用"，Windows 与 Mac 均可用（exFAT 双系统），实测 F 盘 exFAT 启动成功、网关 `/ready` 200。

**0.5.5 踩到并修复的 exFAT 坑（第一手经验，必须沉淀）**：
1. **OpenClaw 原子写 + 严格身份校验在 exFAT 上崩溃**：
   - 现象：打包时手动装 OpenClaw、未跑 exFAT 兼容补丁 → 启动即崩 `path-mismatch`；
   - 根因：OpenClaw 原子写文件时做严格身份校验，exFAT/FAT32 **inode 为 0（无唯一文件身份）**，校验必然不一致；
   - 修复：应用 `patch-portable-filesystem.mjs`（openclaw-cli-shim / diagnostic-stability 两个 bundle 走 `verify-content-with-lock` 兼容路径）；补 `portable-filesystem.mjs` 的 **Windows exFAT/FAT32 零 inode 识别**；补 `.uclaw-runtime-platform` 标记；`runtime-requirements.mjs` 支持三平台标记（win32-x64 + darwin-arm64 + darwin-x64）。
2. **Node 包加载器被内核 ESM 误判**（u-dsh 侧同批修复）：自写启动器 `web-launch.js` 是 CommonJS，被 DSH 内核 `"type":"module"` 当 ESM 加载崩溃 → 改名 `web-launch.cjs` 显式 CommonJS；旧 `--patch` 参数在 DSH 0.2.0-rc.2 已移除，改 `--no-open` 由启动器带 token URL 打开浏览器。
3. **exFAT 无 Unix 执行位**：Mac 上双击 `.command` 可能提示无权限，用户在终端执行 `bash "启动 U-DSH Web.command"` / `bash Mac-Start.command`（0.5.4 的宿主缓存补权限思路同源）。

**仓库**：github.com/dongsheng123132/u-claw（便携版 `portable/`，含 Mac/Windows 启动脚本、config-server、skills-cn 17 个本地化技能）。

**仍待补**：Intel Mac 实机、Finder 首次信任、全部系统授权、每个工具的完整交互、真实模型对话（现用模拟服务验证）；OpenClaw 是否在 data 下建 symlink/junction 仍需按总纲确认（当前方案把整个便携包放 `app/portable-apps/u-claw`，数据随盘 `data/`）。

**未验收前不得宣称"Mac/Linux 完整支持"**（沿用虾盘口径：四平台编译 ≠ 四平台实机验收）。

## 四、通用开发检查清单（新代码逐条对照）

**设计期**
- [ ] 运行时会不会在用户数据目录建 junction/symlink？会 → 设计宿主缓存或换 NTFS-only，别等到用户报错。
- [ ] 大程序（百 MB 级 runtime）是否从 U 盘直接加载？是 → 宿主缓存 + SHA-256 锁定 + 降级路径。
- [ ] 双平台共用一只盘用 exFAT（Mac 不能写 NTFS）；只支持 Windows 时优先 NTFS（junction 需求）或保持 exFAT（无需 junction）。

**实现期**
- [ ] 状态数据（Key/钱包/会话/工作文件）只写盘内 data/，绝不进宿主缓存；不采用退出时同步。
- [ ] 判断文件系统用 `Get-Volume`（Windows）/ `diskutil`（Mac），不要用 `Win32_LogicalDisk.FileSystem`（缓存过期值）。
- [ ] Mac：资源扫描跳过 `._*` / `.DS_Store`；首次复制后补可执行权限；可移除宗卷权限先请求、拒绝给「系统设置」指引。
- [ ] 失败路径必须人话化：探针先行（几毫秒），把"换 NTFS""去设置里开权限"这类动作直接告诉用户，禁止裸抛异常堆栈。
- [ ] 版本锁定：运行时 freeze 版本 + manifest 锁 SHA-256，客户盘不跟踪 upstream nightly。

**验收期（发版硬门槛）**
- [ ] 至少两块真实物理盘对照（exFAT + NTFS，或 exFAT + 目标平台原生格式），同构建同机器，程序文件哈希一致。
- [ ] 换电脑 / 拔插重分配盘符 / 断网启动 / 慢速 U 盘超时，逐项实机记录。
- [ ] 每个数字带口径（启动时间、缓存命中、余额变化），区分"本地回放"与"真实云端"。
- [ ] 四平台编译不等于四平台验收；未验收的平台在文档里如实标注，不宣称支持。

## 五、已踩过不要再踩的坑（追加清单）

- `Set-Content -Encoding UTF8` 写 BOM → `JSON.parse` 挂；用 `WriteAllText(..., UTF8Encoding($false))`。
- Git Bash 里 `/E` 被 MSYS 当路径转换；robocopy 参数用 PowerShell 包一层。
- PATH 上的 GNU tar 读不了 zip；用 System32 的 bsdtar。
- electron-builder `extraResources` 跳过 fileset 根下名为 `node_modules` 的目录，需显式映射 `vendor/harness/node_modules`。
- `missingRequiredPeers` 查的是 node_modules 下所有顶层包，不是根包（根包声明 0 个），别"优化"掉。
- GitHub `releases/latest` 只认非 pre-release——发版时 pre-release 会指向坏包，本地测不出来。
- ad-hoc 签名的 Mac 包每次重建都被视为新程序再次询问权限，正式版用 Developer ID 签名 + 公证。
- OpenClaw/Node 生态的原子写会做严格文件身份校验，exFAT/FAT32 零 inode 必然失败；要么打 `patch-portable-filesystem` 兼容补丁，要么给这类包走"宿主缓存运行、数据留盘"。
- 自写 Node 启动器必须显式 `.cjs` 或包内声明 module 类型，别让内核的 `"type":"module"` 误判；上游 CLI 已移除的参数（如 `--patch`）启动即报错，升级内核后要同步清理。

### 追加（2026-10-15 投盘实测，u-openclaw / u-dsh 发盘版）

- **便携运行时"手动装依赖"会漏掉构建期补丁，必须完整跑 setup 流程**：
  - u-openclaw 的 exFAT 兼容是 `setup.ps1/setup.sh` 里调用 `patch-portable-filesystem.mjs` 给 OpenClaw dist bundle 打补丁（原子写走 `verify-content-with-lock`）。打包时图快用系统 npm 手动装 `openclaw@2026.10.2`，跳过了 setup → 补丁未应用 → 发盘版在 Windows + exFAT 上启动即崩（`FsSafeError path-mismatch`，`@openclaw/fs-safe` 的 strict-file-identity 对 Windows exFAT 的 `dev/ino=0` 必抛错，无宽松路径）。
  - 修复：构建/打包脚本把"跑 setup 或直接跑 patch-portable-filesystem.mjs"列为必做步骤；本盘可直接 `node lib/patch-portable-filesystem.mjs <coreDir>` 补。
- **便携包还缺运行期标记会误触发重装**：`app/core/.uclaw-runtime-platform`（内容 `平台-arch`）缺失时 `runtime-requirements.mjs` 读文件失败 → 判定需要 setup → 调 setup 的 npm → 包内 npm 11.x 崩（`Class extends value undefined`）→ 启动失败。打包后必须写该标记；多平台一体的盘写逗号分隔（`win32-x64,darwin-arm64,darwin-x64`），`runtime-requirements.mjs` 按集合匹配。
- **Windows exFAT/FAT32 的 `stat.ino` 恒为 0**：rename 前后 ino 不变 → 文件系统探测（portable-filesystem.mjs）误判"rename 保持身份"→ 走 strict 崩溃。判定加 `inoUnavailable`（before/after/published ino 全 0）→ 降级 `verify-content-with-lock`。
- **`"type":"module"` 包里的 CommonJS 启动器必崩**：u-dsh 内核 `package.json` 是 ESM，自写 `web-launch.js`（CommonJS `require`）被当 ESM 加载 → `require is not defined`。启动器用 `.cjs` 后缀强制 CommonJS。
- **内核 CLI 参数跨版本会移除**：DSH 0.1.0-rc.7 → 0.2.0-rc.2 移除了 `--patch`，启动器带旧参数 → 内核 `unknown option '--patch'` 退出。升级内核后必须实测 CLI（`--help` / 直接跑）验证参数集。
- **分发回读校验是保护不是慢的元凶**：11 万小文件写 U 盘本身慢；回读校验能抓出坏盘（K 盘 3 万+ CRC 失败 = 坏盘，同 zip 在 F/G 盘全部通过）。别关校验，弃坏盘。
- **zip 中文文件名必须 UTF-8 flag**：bsdtar 写 GBK 名 Windows 解压乱码（启动脚本名失效）；用 Python `zipfile`（自动 UTF-8 flag）分卷/打包。
