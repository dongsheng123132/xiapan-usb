# 网络问题诊断

先明确失败对象：所有网站、某个网站、软件仓库还是模型接口。询问或读取准确错误，不把任何超时直接判成需要代理。

通过 PicoClaw 的 `mcp_xiapan_maintenance_action` 或宿主动作核心读取证据。`network.inspect` 只读取网卡和地址，`internet_verified=false`；`network.diagnose` 检查虾盘云 DNS 和 HTTPS；`drivers.inspect` 在 Windows 离线读取网络类设备、硬件 ID、驱动版本、INF 与故障码，并列出盘内 drivers/ 文件。`network.rescue`（仅 Windows）分层只读检查网卡、网关、外网 IP、DNS、直连与经系统代理的网页，并读取系统代理和 hosts 中对主流网站的自定义指向。仍没有路由表和系统时间检测动作，不得编造读取结果。

未识别且缺驱动的设备也会列出，它不一定是网卡。故障码 0 不证明能上网；文件名相似不证明驱动兼容。按硬件 ID、电脑型号、系统和架构到整机/网卡厂商官网准备驱动，放入 `drivers/<系统-架构>/<厂商-型号>/`，保留来源、许可证和校验值。先尝试有线网络或手机 USB 共享网络，手机连接也可能需要驱动。

`tools.catalog` 给出系统维护工具与官方资源入口的准备状态。`tools.launch` 的 `device-manager` 只申请打开设备管理器：返回 `requires_user_confirmation` 时没有执行；用户在页面确认后只是打开系统界面，不代表已经安装驱动。网络重置、驱动安装、卸载和自动修复仍未实现：网络类问题由系统工具完成，见下文「断网急救」。

## 断网急救（Windows）

网页打不开、而微信/QQ 还能用时，先调用 `network.rescue`。它运行 Open365 网络引擎的 `diagnose`（只读），分层检查网卡、网关、外网 IP、DNS、直连网页与经系统代理的网页，并读取系统代理和 hosts，不改任何配置。

- 结果里的 `next_step` 给出一个要打开的系统工具 `tool_id`（`network-settings` 或 `device-manager`）和 `reason`。用 `tools.launch` 申请打开它；返回 `requires_user_confirmation` 只是申请，用户确认后才打开，打开不代表已经修好。把 `reason` 里该在工具里做的事告诉用户。
- `next_step` 为空，说明引擎测得网页可以打开，不要硬找问题。
- 虾盘自己不执行任何网络修改：不清除或改动代理，不刷新 DNS、续租 IP，不重置 Winsock/TCP-IP，也不安装驱动。修复由系统工具完成，虾盘只推荐并在确认后打开。用户做完后再运行一次 `network.rescue` 复查，只有测试里网页能打开才能说已经恢复。
- 非 Windows 系统上 `network.rescue` 会明确报告不支持，改用 `network.diagnose` 和 `network.inspect`。

按「网卡与链路 → 地址与路由 → DNS → TLS/系统时间 → 代理 → 目标服务」定位。只运行与当前假设有关的检查，避免不断重试不可达服务。

区分断网、服务不可达、认证失败和额度不足。401/403/429 不通过关闭防火墙或重装网卡解决。钱包凭证和代理订阅内容不输出到日志或维护报告。

需要修改时先读出并留存原配置，说明影响范围与恢复办法；通过已授权的确定性动作修改，避免模型自行拼接注册表命令。用户仅请求检查时，检查本身足够，无须额外确认。

验证使用相同的失败对象与相同条件。只有验证通过才能说“已恢复”；网卡变为启用只能说“网卡已启用”。无网络时说明本地工具与已准备的模型仍可使用。
